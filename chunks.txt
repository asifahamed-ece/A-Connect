1	AGENTS.md	0	A+ Connect: an Electron desktop app (Linux/KDE) that mirrors and controls an
Android phone (OPPO Reno 14 5G / ColorOS) by shelling out to `adb` and `scrcpy`.
It is a Linux reimplementation of OPPO's O+ Connect.
2	AGENTS.md	1	## No build step; a few pinned npm dependencies
3	AGENTS.md	2	- There is **no bundler and no build step**, but `package.json` now declares four
  runtime `dependencies` (all `@yume-chan/*` at `3.0.0-beta.5`): `adb`,
  `adb-scrcpy`, `adb-server-node-tcp`, `scrcpy`. They speak the scrcpy protocol
  over ADB from Node, which is how clipboard sync reads the phone clipboard.
  `npm install` is therefore required; `npm start` runs
  `scripts/ensure-deps.js` first and fails with a clear message if they are
  missing.
- Everything else still drives **system binaries** through `child_process`.
  Required on `PATH`: `electron`, `adb` (android-tools), `scrcpy` (5.x, its
  `scrcpy-server` is pushed to the phone), `notify-send` (libnotify), `wl-paste`
  + `wl-copy` (Wayland clipboard) or `xclip` (X11).
- `services/clipboard-bridge.mjs` is **ESM** (the beta libraries are ESM-only)
  and is run as a forked child process; `services/clipboard.js` is CommonJS and
  talks to it over Node IPC (`{ cmd }` down, `{ evt }` up). Do not `require()`
  the `.mjs` from `main.js`.
4	AGENTS.md	3	- Run the app: `npm start` (identical to `npm run dev`; both are
  `electron . --disable-vulkan`). Requires an X11/Wayland session — it opens a
  GUI window, so it will not run headless in CI.
- There is **no test runner, linter, typechecker, formatter, or CI workflow** in
  this repo. Do not claim a verification command passes; the only available
  check is launching the app.
- `setup-usb.sh` — one-time, interactive; enables wireless ADB over USB.
- `test-fixes.sh` / `verify-fixes.sh` — interactive, manual, device-specific
  smoke scripts (they hardcode one serial, see below). They are not a test suite.
5	AGENTS.md	4	- `main.js` — Electron main process. Owns services, the system tray, all IPC
  handlers, and the `adb.startPolling(2500)` device-discovery loop.
- `preload.js` — `contextBridge` exposes the whole API as `window.api`. The
  renderer's only channel to the backend.
- `services/*.js` — backend logic (`adb`, `scrcpy`, `file-transfer`,
  `clipboard`, `notifications`), each an `EventEmitter`.
- `src/index.html`, `src/renderer.js`, `src/style.css` — renderer UI. Plain
  script (no bundler/framework); handlers are global functions called from
  inline `onclick=` attributes.
- `assets/` — raw resources extracted from the official O+ Connect client;
  `assets/icon.png` is used for both the window and the tray.
6	AGENTS.md	5	To add a feature, wire all four layers: a `services/*.js` method → an
`ipcMain.handle` in `main.js` → a `window.api` method in `preload.js` → the
renderer. IPC channel naming is `namespace:action` (`adb:pairWifi`,
`scrcpy:start`); main→renderer pushes use `event:*` (`event:telemetry-updated`).
Keep this convention — the renderer only ever talks through `window.api`
(`contextIsolation: true`, `nodeIntegration: false`).
7	AGENTS.md	6	- **Closing the window does not quit.** `main.js` hides to the tray unless
  `isQuitting` is set; quit via the tray menu or `app.quit()`. A "stuck" running
  app is normal.
- `--disable-vulkan` in the start scripts is deliberate (compositor/GPU issue);
  keep it.
- `services/scrcpy.js` hardcodes the MediaTek encoder
  `--video-encoder=c2.mtk.hevc.encoder` and `--video-codec=h265`. This only
  works on the Dimensity-based target device; other phones need a different
  encoder.
- `test-fixes.sh` and `verify-fixes.sh` hardcode one device serial
  (`adb-XS5TE6ZXLRYTBUM7-...`). Treat them as author one-offs, not reusable.
- Notification sync is `adb logcat` filtering, not a real
  `NotificationListenerService`: notification **text is a placeholder**
  ("New notification"), only the app name is real.
- Clipboard sync is bidirectional and needs **no app on the phone**: the scrcpy
  server runs as `shell`, which Android exempts from the Android 10+
  background-clipboard restriction that forces KDE Connect to ask for a tap.
- **Do not use Electron's `clipboard` module for the desktop side.** On this
  stack it cannot see other clients' Wayland selection (it reads `""`) and its
  writes never reach the compositor. `services/clipboard.js` uses
  `wl-paste`/`wl-copy` (X11: `xclip`) and only falls back to Electron.
- Electron 44's clipboard API is Promise-based (`readText()` returns a Promise,
  `availableFormats()` is gone). If you touch that code path, await it — a
  Promise passed to `webContents.send` serialises to `{}` or throws
  `Failed to serialize arguments`.
- All main→renderer pushes go through `sendToRenderer()` in `main.js`; it
  tolerates a destroyed/reloading window. Sending directly throws
  `Render frame was disposed`.
- The repo is MIT per `package.json`, but there is no `LICENSE` file despite the
  README linking one.
8	AGENTS.md	7	`development-plan.md`, `implementation-roadmap.md`, `project-documentation.md`,
and `protocol-specifications.md` describe an aspirational design — an
unimplemented Rust transport, Qt6/Kirigami UI, D-Bus service, and the reverse-
engineered "Panta" protocol. **None of it is in this codebase.** The real app is
Electron (see `README.md` and `WEEKEND-SPRINT-SUMMARY.md`). Do not implement
against those four files.

67	companion-android/dump/ime-prototype/README.md	1	Android grants background clipboard access to the **default keyboard** and
nothing else: `ClipboardService.clipboardAccessAllowed()` calls
`isDefaultIme()`, which reads `Settings.Secure.DEFAULT_INPUT_METHOD`. An
accessibility service has the same access, but any enabled accessibility
service makes Google Wallet refuse contactless payments, so the keyboard role
is the only route that keeps payments working.
68	companion-android/dump/ime-prototype/README.md	2	That also means the role cannot be handed off: switching to Gboard writes
`DEFAULT_INPUT_METHOD` (`InputMethodManagerService.setInputMethodLocked()` →
`InputMethodSelector.putSelectedInputMethod()`), so a keyboard that "holds the
role and delegates typing" loses the privilege the moment it delegates. The
keyboard the user types on has to be the one with the privilege.

94	docs/companion/keyboard-fork.md	7	Three things had to be fixed for this to work, and all three are easy to
reintroduce:
95	docs/companion/keyboard-fork.md	8	1. **The grant is fixed at install time.** A signature permission is granted to
   a requesting app only if the permission already exists when that app is
   installed. The fork was installed before the companion app that defines the
   permission, so every broadcast was refused with "Permission Denial ... due to
   sender com.aplusconnect.keyboard.debug". Reinstalling the fork after the
   companion app granted it. Install the companion app first.
2. **Do not pass `receiverPermission` to `sendBroadcast`.** Demanding it at send
   time makes the framework check the sender against its own demand, which
   failed on this build even though the grant was present. The receiver's
   manifest `android:permission` is the gate, and it works.

   the main thread, so the service's intent handler ran there, and the socket
   write threw `NetworkOnMainThreadException`, which closed the TLS session on
   every copy. Sends now run on their own thread (`companion-send`).

128	docs/companion/seamless-clipboard-handoff.md	10	1. **There is no accessibility-service exemption.** Six configurations were tested —

167	docs/companion/spike-results.md	6	The measurement was checked against the platform documentation and against what real

168	docs/companion/spike-results.md	7	**There is no clipboard role.** Google was asked for one — AOSP issue 135471818, "offer
'clipboard manager' role", which would let clipboard managers read in the background. It
was closed as *Won't Fix (Obsolete)*. `android.permission.READ_CLIPBOARD_IN_BACKGROUND`
exists, but its protection level is `signature|role`: on this device it is granted only
to apps signed with the platform key (one holder was found,
`com.microsoftsdk.crossdeviceservicebroker`), and no role can be assigned to a normal
app. `cmd role add-role-holder android.app.role.CLIPBOARD` fails with
`Unknown role: android.app.role.CLIPBOARD` — the role does not exist.
169	docs/companion/spike-results.md	8	**The rule is documented and matches the measurement exactly.** From the platform
behaviour: *"Unless your app is the default input method editor (IME) or is the app that
currently has focus, your app cannot access clipboard data on Android 10 or higher."*
The accessibility service is **not** one of the two doors. That matches what this device
did with the service enabled, bound, with and without window-content access.
170	docs/companion/spike-results.md	9	**What real apps do instead** — KDE Connect, the reference implementation, uses a
three-part trick for the phone → PC direction:
171	docs/companion/spike-results.md	10	1. It watches for the *event* of a copy rather than polling the clipboard. Historically
   that meant running `logcat` and looking for the system's clipboard access messages,
   which needs the privileged `READ_LOGS` permission granted through adb. Newer versions
   can use Shizuku for the same job instead of adb.
2. When a copy is detected it launches `ClipboardFloatingActivity` — a transparent,
   non-touchable activity with `FLAG_NOT_TOUCH_MODAL` that raises over other apps and
   takes focus.
3. Because it now has focus, the clipboard read succeeds. It forwards the content and
   finishes immediately.
172	docs/companion/spike-results.md	11	KDE Connect also puts a **"Send clipboard" action on its persistent notification** as the
manual fallback, which is what most users end up using.
173	docs/companion/spike-results.md	12	**The PC → phone direction needs no privilege at all**, because the OS allows background
clipboard *writes*. This matches the measurement exactly, and matches the report that
KDE Connect's clipboard flow works "out of the box" in that direction.
174	docs/companion/spike-results.md	13	| Direction | Mechanism | Privilege needed |
|---|---|---|
| PC → phone | Background clipboard write | **None** — works today, measured |
| Phone → PC | Detect the copy event, then raise a transparent activity that takes focus, read, forward, finish | Accessibility service for the event, focus for the read |
| Phone → PC (alternative) | Be the default keyboard | Default-IME role — measured working, but the user must type with our keyboard |
| Phone → PC (manual) | A "Copy to PC" action on the notification | None — the tap gives the app focus |

than the one the plan assumed: not as a privilege, but as a **copy-event detector**.

188	docs/superpowers/plans/2026-11-11-companion-foundation.md	7	- The companion app must open **zero listening sockets** on the phone. No TCP server, no UDP discovery socket, ever.
- The phone **dials out** to the PC. The PC never opens a connection to the phone.
- Transport is TLS with a pinned certificate. The pin is the SHA-256 of the DER-encoded certificate, rendered as colon-separated uppercase hex.
- Frame format: 4-byte big-endian unsigned length prefix, then UTF-8 JSON. Maximum frame **1 MiB** (1048576 bytes); a longer length header closes the connection.
- Clipboard payloads are capped at **256 KiB** of text. Longer content is truncated and the truncation is explicit in the payload.
- Envelope: `{ "v": 1, "type": "...", "id": "<uuid>", "ts": <epoch ms>, "payload": { } }`. `v` is the protocol major version.
- Message types: `hello`, `hello-ack`, `hello-error`, `clipboard-set`, `ping`, `pong`, `bye`.
- The pairing code is **6 digits** and is valid for **5 minutes**. It is issued and validated
  by the PC (phase P3); in this plan the phone only transmits it.
- The envelope is JSON. **Key order is not significant** — the two implementations may
  serialise object keys in different orders, so conformance is checked on decoded values,
  never on raw bytes.
- Clipboard payload rules (cap, truncation flag, dedupe) live in the protocol layer on both
  sides so the PC and the phone cannot disagree about what may cross the wire.
- Android package name: `com.aplusconnect.companion`. `minSdk 26`, `targetSdk 35`, `compileSdk 35`, JVM target 17.
- Clipboard **content is never written to a log**. Logs carry length and SHA-256 hash only.
- PC-side code follows the repo conventions: `services/*.js` are CommonJS `EventEmitter`s, IPC channels are `namespace:action`, `preload.js` exposes `window.api`, renderer code is a plain script with no bundler.
- Commit messages: one line, imperative, ≤ 72 characters, no attribution trailers.
- The desktop app's existing ADB clipboard path must keep working unchanged throughout this plan.

 * It polls the clipboard from a background thread, which is exactly the read
 * the real app will perform.

259	docs/superpowers/plans/2026-11-11-companion-foundation.md	78	private val poller = object : Runnable {
        override fun run() {

            handler.postDelayed(this, POLL_INTERVAL_MS)
        }
    }
260	docs/superpowers/plans/2026-11-11-companion-foundation.md	79	override fun onServiceConnected() {

262	docs/superpowers/plans/2026-11-11-companion-foundation.md	81	private fun readOnce() {
        val result = try {
            val manager = getSystemService(Context.CLIPBOARD_SERVICE) as ClipboardManager
            val clip = manager.primaryClip
            if (clip == null || clip.itemCount == 0) {
                "EMPTY"
            } else {
                val text = clip.getItemAt(0).coerceToText(this).toString()
                val hash = sha256(text)
                // Length and hash only - never the content.
                if (hash == lastHash) {
                    "SAME len=${text.length} sha=${hash.take(12)}"
                } else {
                    lastHash = hash
                    "OK len=${text.length} sha=${hash.take(12)}"
                }
            }
        } catch (e: Exception) {
            "DENIED ${e.javaClass.simpleName}: ${e.message}"
        }
        Log.i(TAG, "read result: $result")

object FrameCodec {
    const val MAX_FRAME_BYTES = 1024 * 1024
354	docs/superpowers/plans/2026-11-11-companion-foundation.md	173	fun encode(message: ProtocolMessage): ByteArray {
        val body = message.toJson().toString().toByteArray(StandardCharsets.UTF_8)
        require(body.size <= MAX_FRAME_BYTES) { "frame too large: ${body.size}" }
        val buffer = ByteBuffer.allocate(4 + body.size)
        buffer.putInt(body.size)
        buffer.put(body)
        return buffer.array()
    }
355	docs/superpowers/plans/2026-11-11-companion-foundation.md	174	fun decode(frame: ByteArray): ProtocolMessage {
        require(frame.size >= 4) { "frame too short" }
        val buffer = ByteBuffer.wrap(frame)
        val length = buffer.int
        require(length in 0..MAX_FRAME_BYTES) { "illegal frame length: $length" }
        require(frame.size >= 4 + length) { "truncated frame" }
        val body = String(frame, 4, length, StandardCharsets.UTF_8)
        return ProtocolMessage.fromJson(org.json.JSONObject(body))
    }
356	docs/superpowers/plans/2026-11-11-companion-foundation.md	175	fun readFrom(input: InputStream): ProtocolMessage {
        val header = ByteArray(4)
        DataInputStream(input).readFully(header)
        val length = ByteBuffer.wrap(header).int
        require(length in 0..MAX_FRAME_BYTES) { "illegal frame length: $length" }
        val body = ByteArray(length)
        DataInputStream(input).readFully(body)
        return decode(header + body)
    }

  const body = Buffer.from(JSON.stringify(toJson(message)), 'utf8');

    throw new Error(`frame too large: ${body.length}`);
  }

  frame.writeInt32BE(body.length, 0);
  body.copy(frame, 4);

  if (length < 0 || length > MAX_FRAME_BYTES) {
    throw new Error(`illegal frame length: ${length}`);
  }

  const parsed = JSON.parse(frame.subarray(4, 4 + length).toString('utf8'));
  return {
    version: parsed.v,
    type: parsed.type,
    id: parsed.id,
    ts: parsed.ts,
    payload: parsed.payload || {},
  };

533	docs/superpowers/plans/2026-11-12-companion-services.md	6	- **No ADB, no developer options, no wireless debugging.** Every feature must work
  with the phone in its shipping state. ADB may be used by a developer to *check*
  something, never as a dependency of the feature.
- **No accessibility service** in the shipping app: Google Wallet refuses
  contactless payments while any accessibility service is enabled
  (`AccessibilityManager.getEnabledAccessibilityServiceList()`).
- **The phone never listens.** The companion client dials the PC; no inbound port,
  no listening socket, ever.
- **One transport per event.** If the companion is connected, the event comes over
  the companion channel; otherwise over the existing ADB path. Never both, never a
  duplicate.
- **Frame format:** 4-byte big-endian length prefix, then a 1-byte frame kind, then
  the payload. Kind `0` = UTF-8 JSON (as today), kind `1` = binary. The frame limit
  stays 2 MiB. `PROTOCOL_VERSION` goes to `2`; both sides ship together.
- **Permissions are optional and explained.** Notification access, screen projection
  and the file picker are each requested from the app's Settings tab, in plain
  English, with the reason. The app works without any of them.
- **No new runtime dependencies** on the phone unless a task says otherwise; the app
  already has Compose, CameraX and ZXing.
- **The keyboard fork is a separate APK** (GPL-3.0, `com.aplusconnect.keyboard`); the
  companion app stays MIT. Do not move keyboard code into this app.
- **Desktop verification is `node scripts/<name>.js`** — there is no test runner in
  this repo. Android verification is `./gradlew :app:testDebugUnitTest`.
- **Commit messages: one imperative line, ≤ 72 characters**, no body, no trailers.

535	docs/superpowers/plans/2026-11-12-companion-services.md	8	1. **A notification that arrives while the PC is offline.** It must be queued and
   delivered once, not dropped and not replayed as a duplicate.
2. **Notification content is private.** It must never be written to a file on the PC,
   and must never be sent when the companion channel is not connected.

   at any moment; the capture must die then, not keep the screen.

|--------|------------|
| Peer on the same Wi-Fi connects to the phone | The phone listens on nothing. No inbound port exists. |
| Peer on the same Wi-Fi reads the clipboard traffic | TLS 1.3 with a pinned certificate; the phone refuses any certificate that does not match the pinned fingerprint. |
| Rogue peer races the pairing (MITM) | The user compares a **6-digit code** and the **SHA-256 fingerprint** shown by both sides. A rogue peer cannot produce the PC's fingerprint, so it cannot complete the handshake. |
| Peer replays an old session | Each handshake carries a fresh random nonce that the PC echoes in `hello-ack`, binding the two messages to a single attempt. TLS session keys are negotiated per connection. |
| Anyone can pair a rogue PC | Pairing requires the physical 6-digit code; after pairing, the PC is pinned by fingerprint and cannot be substituted. |
| Clipboard content in logs | Clipboard payloads are never written to the app log; only lengths and hashes. |
| College Wi-Fi with client isolation | USB tethering gives a private point-to-point link; the same protocol is used over a different interface. |
| A malware app on the phone reads the clipboard | Out of scope — this is a capability the user grants deliberately to a trusted app. Documented in the app's privacy section. |
601	docs/superpowers/specs/2026-11-11-companion-apk-design.md	16	**Certificate handling.** The PC generates a self-signed certificate on first run
(`openssl req -x509 -newkey rsa:2048 -nodes`, 10 years) and caches it in
`~/.config/aplus-connect/companion/`. The fingerprint is the SHA-256 of the DER-encoded
certificate, shown as colon-separated hex — the same shape users already recognise from
Bluetooth pairing screens.
602	docs/superpowers/specs/2026-11-11-companion-apk-design.md	17	**Pairing code.** The PC generates a 6-digit code valid for 5 minutes. The phone sends
`hello` with the code + its own device id. The PC compares the code, replies `hello-ack`
containing the certificate fingerprint. The fingerprint is what the phone pins; the
transport security itself comes from TLS.
The phone stores the fingerprint; every later connection must present a matching
certificate or the connection is refused. A reply without a well-formed fingerprint is
refused outright: pinning an empty string would wedge the phone, refusing every later
connection with no way back.

731	protocol-specifications.md	0	# A+ Connect - Panta Protocol Specifications
732	protocol-specifications.md	1	The Panta protocol (also known as O+ Connect, Multi-Screen Connect, or OPPO PantaConnect) is a custom binary framing protocol developed by OPPO for cross-device connectivity. This document details the protocol structure based on reverse engineering of OPPO binaries.
733	protocol-specifications.md	2	The core unit of communication in the Panta protocol is the PlainControl frame:
734	protocol-specifications.md	3	```
struct PlainControl {
    uint8_t server;      // 1 if frame originates from server, 0 from client
    uint8_t hello;       // 1 if this is a hello message, 0 otherwise
    uint8_t agent[4];    // 4-byte agent identifier
    uint32_t protobuf_len; // Length of Protobuf payload
    uint8_t protobuf_data[protobuf_len]; // Protobuf-encoded message
};
```
735	protocol-specifications.md	4	| Field | Size | Description |
|-------|------|-------------|
| `server` | 1 byte | Direction flag (server=1, client=0) |
| `hello` | 1 byte | Hello message indicator |
| `agent` | 4 bytes | Agent identifier (e.g., "SC1.0") |
| `protobuf_len` | 4 bytes | Length of Protobuf payload |
| `protobuf_data` | variable | Protobuf-encoded message |
736	protocol-specifications.md	5	The `agent` field contains 4-byte identifiers for different OPPO components:
737	protocol-specifications.md	6	- `"SC1.0"` - Screen casting service
- `"ONET"` - OPPO Network service
- `"PANT"` - Panta protocol service
- `"DEV"` - Device management service

762	protocol-specifications.md	31	- All multi-byte values are stored in **little-endian** format

- Frames are sent over TCP without additional framing (delimited by message length)
